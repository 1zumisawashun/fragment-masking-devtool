PRのレビューコメントに対応するための対話的なワークフローを提供する。対象はCopilotと人間レビュアーのコメントで、CIボットなど他のbotのコメントは対象外。

## Step 1: PR番号の解決

引数でPR番号が渡されていればそれを使う。渡されていなければ現在のブランチのPRを使う。

## Step 2: レビューコメントを取得する

`./references/fetch-comments.md` をReadし、手順に従ってPR情報・レビューコメント・スレッドIDを取得する(ブランチの自動切り替え・Copilot/人間レビュアーへのフィルタリング・返信コメントの除外・outdatedコメントの扱いもここに含まれる)。取得できたらStep 3に進む。

## Step 3: 各コメントを分析して修正プランを立てる

各コメントについて:

0. **対応不要なコメントの除外**
   - 「LGTM」「nice catch」など、修正を要求せず確認・感謝のみのコメント(主に人間レビュアーのコメントで発生する)は自動的にskip扱いとし、A/Bのプランは提示しない
   - 実質的な指摘を含むコメントのみ、以降の分析対象とする

1. **コメント内容を分析**
   - 指摘内容(何が問題か)
   - 提案内容(どう修正すべきか)
   - 対象ファイル・行番号

2. **修正プランを提案**

   各コメントに対して、以下の2つのオプションを提示:

   **オプション A: 実装による修正**
   - 具体的な修正内容
   - 修正対象ファイルとコード
   - 修正の影響範囲

   **オプション B: コメントでの返信**
   - 返信文の提案
   - 返信理由(なぜ実装修正しないか)

3. **推奨オプションを提示**

   以下の基準で推奨を判定:
   - 明確で機械的な修正(タイポ、フォーマット、明らかなバグ)→ オプション A 推奨
   - 設計判断が必要、トレードオフがある、議論の余地がある → オプション B 推奨
   - 既存のコードベースのパターンと矛盾する → オプション B 推奨

## Step 4: プランをユーザーに提示

以下のフォーマットでプランを提示する。

```
## レビューフィードバック修正プラン

### コメント #1 (file.ts:123)
**指摘内容:** {コメント本文の要約}

**オプション A: 実装修正** ⭐️ 推奨
- 修正内容: {具体的な修正}
- 影響範囲: {影響するファイル・機能}

**オプション B: コメント返信**
- 返信案: {提案する返信文}
- 理由: {実装修正しない理由}

---

### コメント #2 (file2.ts:456)
...

---

## 次のステップ

以下のように選択してください:
- 1,2,5 → A (実装修正)
- 3,4 → B (コメント返信)
- 6,7 → skip (手動対応)
```

ユーザーからの入力を待つ。

## Step 5: 選択に基づいて実行

`1,2,5 → A` のような入力を解析し、`./references/apply-fix.md` をReadして、選択されたオプション(A/B/skip)ごとの実行手順に従う。**commit・pushは必ずこのステップで、ユーザーの選択を受け取った後にのみ行う。**

## Step 6: 元のブランチに戻る

Step 2でPRのブランチに切り替えていた場合は、元のブランチに戻る。

```bash
git checkout $ORIGINAL_BRANCH
```

## Step 7: 実行結果のレポート

```
## 実行結果

### 実装修正したコメント (3件)
- コメント #1: {要約} → コミット {sha}
- コメント #2: {要約} → コミット {sha}
- コメント #5: {要約} → コミット {sha}

作成したコミット:
- {commit_sha}: fix: レビュー指摘に対応 (#1, #2, #5)

### コメント返信したコメント (2件)
- コメント #3: {要約} → resolve済み
- コメント #4: {要約} → resolve済み

### 手動対応が必要なコメント (2件)
- コメント #6: {要約}
  リンク: {comment_url}
- コメント #7: {要約}
  リンク: {comment_url}

## 次のアクション
{手動対応が必要なコメントがある場合}
手動対応が必要なコメントを確認してください。
```

## 重要なガイドライン

### 実行タイミング

commit・pushは常にStep 4(プラン提示)より後、Step 5(選択に基づいて実行)でのみ行う。ユーザーの選択を経由しない自動commit・pushはしない。

### コメント返信のベストプラクティス

コメント返信を提案する際は、丁寧かつ建設的に(指摘への感謝・判断理由の説明・必要に応じた代替案の提示)、具体的に(既存パターンや型定義など根拠を明示)、簡潔に(箇条書き中心、長すぎる説明は避ける)まとめる。

実装修正 vs コメント返信の推奨基準はStep 3参照。

### 日本語での対応

- すべての出力は日本語で行う
- コミットメッセージは日本語
- PRコメント返信も日本語
- ただし、コード自体は英語のまま

## 使用例

```bash
# PR #8 のレビューコメントに対応
/review-fix 8

# 現在のブランチのPRに対応(PR番号を自動推測)
/review-fix
```
