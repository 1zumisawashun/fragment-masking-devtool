# new-skill

skillを作る作業そのものを型にはめるskill。中身がバラバラな手順書を量産しないために、
新規作成・既存skillの見直しのどちらでも、以下の4項目を**具体例つきで**必ず埋めてから
`SKILL.md` を書く。

- **判定原則**: 迷ったときの判断基準。作業を始める前に渡す
- **停止条件**: 機械的に確認できる完了条件。ここまでAIが自走する
- **Gate**: 人間が判断する関門。ここだけ人間が出る
- **ログ**: 状態と判断の記録。コンテキストの外に置く

## 型

- **判定原則**: 4項目のうち1つでも抽象的なまま（例:「良い感じに判断する」「必要に応じて」）
  提示された場合は、そのまま採用せず、具体例を求めて1回だけ押し返す。2回目もなお抽象的なら、
  ユーザーの言葉を尊重しつつ自分から具体例のたたき台を出して確認を取る — 埋まらないまま
  スキップしない。
- **停止条件**: 4項目とも埋まり（各項目に最低1つの具体例があり）、`## 型` セクションと
  `## 進め方` の内容に矛盾がない（例: 判定原則で言っていることと進め方の手順が食い違わない）。
- **Gate**: 完成した `SKILL.md` を書き込む前に、4項目の内容をユーザーに提示して確認を取る。
  それより前（ヒアリング・下書き作成）はagentが自走してよい。
- **ログ**: 作られた `SKILL.md` 自体が唯一のログ。作成理由や検討過程を別ファイルに残す必要は
  ない（このskillの由来だけは、必要なら `README.md` に残す — [[local-grill-me]] の例を参照）。

## 進め方

### 1. 対象を特定する

引数が一言のskill説明なら新規作成、既存skillのパス（例: `.claude/skills/implement`）なら
見直しモード。どちらも不明なら質問する。

### 2. スコープを決める

このリポジトリの `.claude/skills/`（project scope）に置くか、`~/.claude/skills/`
（user scope、全プロジェクト共通）に置くか。skillの内容がこのリポジトリ固有（例: このrepoの
GitHub issue運用に依存する）ならproject、汎用ならuserを勧める。迷う場合はユーザーに確認する。

### 3. 4項目を具体例つきでヒアリングする

新規作成なら以下を1項目ずつ尋ねる。既存skillの見直しなら、まず現状の `SKILL.md` を読み、
「進め方」に書かれている内容から4項目を自分で抽出した案を作り、それをユーザーに確認してもらう
形にする（ゼロから聞き直さない）。

- **判定原則**: 「このskillが実行中に迷いうる場面はどこか。そのときどう判断するか」を尋ね、
  `もし<状況>なら<判断>` の形の具体例を最低1つ出してもらう。
- **停止条件**: 「どうなったら完了とみなすか」を尋ね、コマンドの成否・ファイルの有無・
  チェックリストの完了など、**人が見なくても機械的に確認できる形**で言い換える。「レビューが
  十分」のような主観的な表現のまま採用しない。
- **Gate**: 「このskillの中で、人間でなければ判断できない一点はどこか」を尋ねる。複数出てきた
  場合は、そのうちどれが本当に外せないGateかを絞り込み、残りは判定原則に委譲できないか
  一緒に検討する（Gateは薄く保つ）。
- **ログ**: 「このskillの実行結果・判断根拠を、次にこのskillや別のskillが読む必要があるとき、
  どこを見ればよいか」を尋ねる。「チャットのやり取りを覚えておく」は不可 — 必ずファイル・
  issue・PR・commitのようなコンテキストの外にある置き場所を答えてもらう。

### 4. `SKILL.md` を組み立てる

```markdown
---
name: <kebab-case>
description: <いつ使うか。ユーザーの発言例や明示呼び出しを含める>
argument-hint: <引数の説明>
---

# <name>

<このskillが何をするか、1〜2文>

## 型

- **判定原則**: ...(具体例つき)
- **停止条件**: ...(機械的に確認できる形)
- **Gate**: ...(最小限の1点)
- **ログ**: ...(具体的な置き場所)

## 進め方

### 1. ...
```

「進め方」の各ステップは、`## 型` で定義した4項目と矛盾しないように書く（例: 判定原則で
「調べれば分かることは聞かない」と言っているのに、進め方でいきなりユーザーに聞く手順になって
いないか確認する）。

### 5. 書き込む前に確認する（Gate）

4項目と全体の下書きをユーザーに提示し、確認を取ってから `Write` する。

### 6. 報告する

作成/更新したファイルのパスと、スコープ（project/user）を伝える。

## 注意

- 4項目を機械的に埋めるだけの作業にしない。具体例が出てこない項目は、そのskillの設計自体が
  まだ曖昧である signal なので、無理に言葉を当てはめず設計に立ち返る。
- 既存skillの見直しでは、動いている「進め方」の中身を壊さない。型は既存の手順を整理・
  可視化するためのものであって、書き直すためのものではない。
