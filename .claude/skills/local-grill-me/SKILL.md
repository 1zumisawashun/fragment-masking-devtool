# local-grill-me

GitHub issue の「why」を、調査とgrillingインタビューによって埋め、issueに書き戻す。これは
`local-grill-me` → `breakdown` → `implement` パイプラインの1段階目（この3つをまとめて振り分ける
入口として `refinement` もある）。

1. **local-grill-me**（このskill） — why → スコープされたissue本文
2. `breakdown` — スコープ済みissue → ネイティブなGitHub sub-issue群
3. `implement` — 1つのsub-issue → ブランチ作成・実装・PR

> 由来: [mattpocock/skills](https://github.com/mattpocock/skills) の `grill-me` / `grilling`
> （MIT License, Copyright (c) 2026 Matt Pocock）を、GitHub issueの調査・書き戻しに合わせて
> 手を加えたもの。実際のインタビュー技法そのものは `gh skill install mattpocock/skills
skills/productivity/grilling --agent claude-code --scope user` でグローバルに導入した
> `grilling` skill（`~/.claude/skills/grilling/SKILL.md`）を呼び出して使う。`gh skill update`
> でMatt側の更新に追従できる。

## 型

- **判定原則**: ステップ1の調査で答えが分かることは質問しない。質問するのは「コード＋一言の
  whyだけでは本当に曖昧」かつ「答えによって何を作るか／どう作るかが変わる」の両方を満たす
  論点だけ。独立した論点は想定回答つきでバッチにし、依存する論点だけ1つずつ確認する（詳細は
  下記「質問フォーマット」）。ユーザーが「お任せします」と言っても黙って決めず、推奨案を示して
  確認を取る。
- **停止条件**: `grilling` のfrontierが空になった（設計木の全ての枝を訪問し、暗黙の仮定が
  残っていない）、かつユーザーが「共通理解に達した」と明示的に確認した。
- **Gate**: 停止条件を満たした後、issue本文を書き戻す前の、ユーザーによる「共通理解に達した」
  という明示確認。これより前（調査・質問構築・下書き作成）はagentが自走する。
- **ログ**: issue本文そのもの（背景・方針・タスク・未決定）が唯一の永続ログ。判断根拠を会話の
  中だけに残さず、必ずissueに書き戻す。

## 入力

このskillに渡される引数は以下のいずれか。

- **GitHub issue番号** — 既存のissue（タイトルだけでほぼ空のことが多い）の本文を埋める。
  `gh issue view <n> --json number,title,body,url` で取得する。
- **フリーテキスト** — issueがまだ無い状態の一言のwhy（例: `"admin をミニアプリ化したい"`）。
  タイトルが自明でなければユーザーに短いタイトルを確認し、
  `gh issue create --title "..." --body ""` で先にissueを作ってから続ける（書き戻し先の
  issue番号を必ず用意する）。

引数が何も渡されなかった場合は、何もする前にユーザーに一言のwhyを尋ねる。

## 進め方

### 1. インタビューの前に調査する

`grilling` は「事実探しは agent の仕事、ユーザーの仕事は決定だけ」という前提に立っている。
質問を始める前に、issueタイトルが示すコード領域を実際にgrep/読み込みし、既存のscaffolding・
類似の先行実装・制約を確認しておく。ここで調べた事実は、次のステップで `grilling` に渡す
コンテキストになる。調査で分かったことを短くまとめて共有してから次に進む。

### 2. `grilling` skillを呼んでインタビューする

`Skill` ツールで `grilling` を呼び出す。渡すお題は「このissueをどうスコープするか」とし、
ステップ1で見つけた事実（既存の制約・選択肢）を伝える。design tree / rounds / frontierという
`grilling` の設計手法（決定を木構造にマッピングし、frontierを計算し、事実探しは自分の仕事で
ユーザーには決定だけを委ねる）はそのまま使う。ただし1ラウンドあたりの**質問の出し方**は、
`grilling` 標準の「ラウンド全体に明示回答を必須とする」形式ではなく、下記の「質問フォーマット」
に置き換える — GitHub issueのスコーピングでは、この方が往復を減らせるため。

frontierが空になり「共通理解に達した」とユーザーが確認したらセッション終了。ステップ3に戻って
issue本文の下書きに進む。

#### 質問フォーマット

**独立した論点はバッチにまとめる。** 他の未回答の質問に依存しない論点は、すべて1つのバッチに
まとめて出す。それぞれの質問に対して自分の**想定回答**（現時点で得られている情報から見て
最も妥当なデフォルト）を明記する。ユーザーはその想定が誤っている、または調整が必要な質問にだけ
返信すればよい — 何も言われなかった質問は、想定回答が採用されたものとして扱う。

**依存関係のある論点は1つずつ尋ねる。** ある決定が次の決定の前提になっている場合は、それだけを
単独で尋ね、その回答を待ってからその枝を先に進める。

**コードベースを調べれば分かることは尋ねない。** 質問する代わりに調べる（ステップ1の続きとして
サブエージェントに調べさせてもよい）。

### 3. issue本文を下書きする

後で `breakdown` が機械的に読み取れる構造にする（文章の綺麗さより重要）。

```markdown
## 背景

なぜこれをやるか。ステップ1の調査に基づいた1〜2段落。

## 方針

`grilling` セッションで決まった論点を「決定事項」として記述する（未決の疑問文にしない）。
自明でない理由は一言添える。

## タスク

### <フェーズ/グループ1の名前>

- [ ] 具体的で、単独で実装可能なタスク
- [ ] ...

### <フェーズ/グループ2の名前>

- [ ] ...

## 未決定（別issueで検討）

`grilling` セッションで明示的に先送りされた事項。ここに書いておかないと静かに抜け落ちる。
```

タスク配下の `###` グループ1つが、後で `breakdown` を実行したときにsub-issue 1つになる。
そのため各グループは1つのPRになりうる粒度に収める。チェックボックス1個だけの些末なグループを
作ったり、無関係な作業を1つのグループに詰め込んだりしない。

### 4. 書き戻す

`gh issue edit <n> --body "$(cat <<'EOF' ... EOF)"`（ヒアドキュメントを使い、日本語テキストや
markdownでのシェルエスケープ問題を避ける）。`grilling` セッションでユーザーが「共通理解に
達した」と確認した後は、直接書き戻してよい。

### 5. 報告する

issueのURLと、次に `breakdown 72` のようなフォローアップが可能である旨を一言添える。

## 注意

- 「方針」の答えを勝手に想像で埋めない。`grilling` セッションで埋まらない本当のギャップは、
  埋めずに未決定に置く。
- issue本文はユーザーが書いている言語（このリポジトリでは日本語）に合わせる。`grilling`
  自体は英語の指示だが、実際のインタビューはユーザーの言語で行ってよい。
